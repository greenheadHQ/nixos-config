## 이 계획서의 성격과 재개 트리거

- **이 창의 실행이 이슈 #917의 재개 트리거다.** #917(update-script 4서비스
  골격 통합)은 "실 서비스 업데이트 = 데이터 정합성 위험 + 유지보수 창 필요"로
  자율 머지가 보류됐고(#917 코멘트 "왜 자율 머지 부적합인가"), 실경로 검증
  절차가 같은 코멘트에 인계됐다. 운영자가 이 창을 잡으면 **본 계획서를 따라**
  세 작업을 고정 순서로 실행한다.
- `plans/016`도 "다음 유지보수 창에서 드릴 1회차 실행을 재개 트리거로 삼는다"
  (016 Step3 "재개 트리거 & 유지보수 창 묶음 권고")고 명시한다. `plans/005`도
  마이그레이션을 #917·복원 드릴과 "한 창에 묶는 것"을 권고한다(005 §2.5).
  → 세 작업이 같은 창을 재개 트리거로 공유한다.

## Step 2.1 산출: 고정 실행 순서와 근거

**순서: A(복원 드릴) → B(DB 마이그레이션) → C(#917 실경로 검증).** 근거:

1. **A를 먼저** — 백업 신뢰를 실증으로 확보한다. B(마이그레이션)의 롤백 재료가
   바로 DB `.dump`인데(005 §2.4), 그 `.dump`로 실제 복원이 되는지 확인하지
   않은 채 B에 들어가면 안전망이 유효한지 모른 채 가장 위험한 작업을 하는 셈이다
   (016 Step3 재개트리거: "마이그레이션이 DB를 건드리기 전에, 현재 백업으로
   실제 복원이 되는지 확인해야 안전망이 유효하다"). **A 실패 = 이후 전면 중단.**
2. **B를 다음** — 세 작업 중 가장 위험(실서비스 중단 + DB 스키마 변경). 직전
   A에서 검증한 `.dump`가 롤백 재료다(005 §2.1·§2.4). B를 C보다 앞에 두는 이유:
   B가 postgres 이미지를 VectorChord로 바꾸므로, C의 immich 실경로 검증을
   **마이그레이션 후 새 DB 이미지 기준**으로 하면 이중 작업이 없다. 또한 immich
   서버가 version-check로 v3.x(pgvecto.rs 제거 절벽)에 도달하기 전에 마이그레이션을
   끝내야 안전하다(005 §요약, §1.2).
3. **C를 마지막** — 위험 오름차순(copyparty→uptime-kuma→karakeep→immich)으로
   골격을 점진 검증(#917 §5). immich 실경로는 이미 마이그레이션된 DB 위에서 검증.

**입력 보고서에서 순서를 뒤집을 근거를 찾았는가**: 없음. 세 입력 모두 "드릴
먼저"에 정합한다(016 Step3, 005 §2.5). 다만 아래 중대 발견이 **드릴 B의 범위와
창 전 준비**에 영향을 주므로 순서 변경이 아니라 **사전 게이트**로 흡수한다.

### 중대 발견(016)이 이 창에 주는 제약 — Immich 원본 사진 무백업

- **사실**: Immich 원본 사진/영상 약 **105G가 SSD(`dockerData`/`upload-cache`)에만
  존재하고 어떤 백업도 없다.** `disko`는 재설치 시 SSD(NVMe)를 포맷하므로, 재해
  시 DB 덤프(HDD)는 남아도 **원본은 영구 소실**된다(016 §요약 1, §Step1 행 #1,
  §Step4 (A)). 상수/주석의 이름("upload-cache")과 달리 실제 원본 라이브러리
  대부분이 여기 있다(016 §"plan 016 Current state와의 차이").
- **이 창에 대한 함의(판단, 순서 변경 아님)**:
  - **B(DB 마이그레이션)는 postgres 볼륨만 인플레이스로 건드리며(005 §2.2)
    `upload-cache`(원본)를 직접 만지지 않는다.** 따라서 마이그레이션이 원본을
    직접 위험에 빠뜨리지는 않는다. 그러나 창 전체가 105G 원본이 얹힌 SSD
    위에서 진행되므로, 원본의 2차 사본 없이는 창을 시작하지 않는다(아래 게이트).
  - **필수 사전 게이트 (하드 스톱)**: 016 §Step4 (A)가 "단일 최우선 시정"으로
    지목한 **원본 105G의 SSD 밖(HDD 또는 외장) 사본이 존재해야 창을 시작할 수
    있다** — 표준 경로는 `plans/019-immich-originals-mirror.md`(HDD 일일 미러)의
    머지·적용 + 초회 미러 완료다(동등한 사본이면 수단 무관). **미충족 시 창
    전체를 시작하지 않는다(중단)** — 리스크 수용·기록으로 대체할 수 없다.
  - 게이트 충족 시 **드릴 B(파일 샘플 복원)가 원본까지 커버**한다: 019 미러
    (또는 동등 사본)에서 무작위 원본 샘플을 복원해 `sha256` 대조한다(016 드릴B).

## 작업 A: 백업 복원 드릴

- **시작 조건**: "시작 전 준비"의 Immich DB 백업 항목 통과. 임시 postgres/임시
  DB명 사용 준비 (016 §Step3 "어디서").
- **절차**(016 §Step3 재사용, plan 001 문서 절차):
  1. 드릴 A — DB 덤프 복원: `.claude/skills/running-containers/references/immich-update.md`의
     "재해복구 복원 — 일일 백업(`.dump`)" 절 그대로 재사용
     (`pg_restore --list` → 임시 DB 복원 → 주요 테이블/row 확인) (016 드릴A).
  2. 드릴 B — 파일 샘플 복원: 2차 사본(필수 사전 게이트가 보장하는 019 미러
     또는 동등 사본)에서 무작위 원본 N개(예 5개) 복원해 `sha256` 대조 (016 드릴B).
  3. 드릴 C — 시크릿 재암호화 확인(경량): 사용자 키 보유 머신에서 `.age`
     재암호화가 동작함을 1회 확인 (016 드릴C).
- **성공 기준**(016 각 드릴):
  - 드릴 A: ① `pg_restore --list`가 유효 TOC 출력 ② 임시 DB 복원 exit 0
    ③ `assets`/`users` 등 주요 테이블 존재 + row count > 0.
  - 드릴 B: 복원 파일 `sha256`이 소스와 일치(수행한 대상 한정).
  - 드릴 C: 재암호화 후 대상 시크릿 정상 복호화.
- **실패 시 행동**:
  - **드릴 A 실패 → 창 전체 중단**(백업 신뢰 미확보 = B의 롤백 재료 무효)
    (016 드릴A "실패 시 즉시 중단"; 005 §2.4가 `.dump`에 의존).
  - 드릴 B 실패(사본에서 샘플 복원 불일치) → **창 전체 중단** — 필수 사전
    게이트가 보장해야 할 사본의 신뢰가 무너진 것이므로, 사본 재생성·원인 규명
    후 창을 다시 잡는다 (016 §Step4 (A)).
  - 드릴 C 실패 → 기록. 마이그레이션은 DB만 건드리므로 진행 가능하나 시크릿
    복구 규율 이슈로 별도 후속 (016 §"제외 항목 근거" #10).

## 작업 B: Immich DB 마이그레이션 (pgvecto.rs → VectorChord)

- **시작 조건**: 작업 A 드릴 A 통과. premigration `.dump` 스냅샷 확보. 스테이징
  리허설로 0.2.0→전환용 이미지 자동 마이그레이션 경로 사전 확인(005 §2.2
  `[UNVERIFIED]` — 버전 정합 리스크).
- **절차**(005 §2.2–2.3, 코드 변경은 별도 plan에서 — 본 창은 절차 실행):
  1. 중지: `systemctl stop podman-immich-{server,ml,postgres}.service` 순 (005 §2.2).
  2. 이미지 교체: `tensorchord/pgvecto-rs:pg16-v0.2.0` → 전환용
     `ghcr.io/immich-app/postgres:16-vectorchord…-pgvectors…`(반드시 `-pgvectors`
     전환용 태그; 최신 순수 `-pgvector` 태그는 기존 벡터 못 읽음) (005 §1.3, §2.2).
  3. 볼륨 **인플레이스 재사용**(같은 PG major 16); `--shm-size=128m` 검토;
     `DB_VECTOR_EXTENSION` 미설정 유지 (005 §2.2).
  4. `podman pull` → postgres 기동(헬스 대기) → ml → server. 기동 중 DB 자동
     마이그레이션 (005 §2.2 "교체 후").
- **성공 기준(기동 후 검증, 005 §2.3)**:
  - 서버 헬스: `/api/server/version` 200 (005 §2.3.1).
  - `\dx`에서 `vchord` 로드, pgvecto.rs(`vectors`) 미사용 (005 §2.3.2).
  - 웹 UI 자연어/유사 이미지 검색 + 얼굴 인식 결과 정상 (005 §2.3.3).
  - postgres 로그 ERROR 부재 (005 §2.3.4).
  - 일일 백업 서비스 수동 실행 후 새 `.dump` 무결성 통과 (005 §2.3.5).
- **실패 시 행동**(005 §2.4): server/ml/postgres 전부 stop → 이미지 구 태그
  원복 → 볼륨 손상 시 premigration `.dump`를 `pg_restore --clean --if-exists`로
  복원(plan 001 절차) → 헬스체크 통과 후 복귀. **B 롤백 후 창 종료**(C는 새 DB
  이미지 전제라 미진행).

  라이브 컨테이너 가동. update-orchestrator + thin 래퍼 구현 완료 (#917 §3, §5).
- **절차**(#917 코멘트 "권장 진행 절차" + §5):
  1. copyparty → uptime-kuma → karakeep → immich 순으로 마이그레이션. 각 단계
     후 앞선 서비스 dry-run 모두 재검증(`diff` empty 기대) (#917 §5).
  2. 각 서비스 **실제 1회 업데이트**로 §6 divergence 체크리스트 검증 (#917 §6):
     - uptime-kuma: 백업 `gzip -t` + 크기 + 복원 + 모니터 정상 + 7일 정리.
     - karakeep: `--ack-bridge-risk`로 실행, bridge 3유닛 active.
     - immich: pg_dump 무결성 + ML 기동 + API health + 4-step 순서.
     - copyparty: 백업 없는 저위험 1회 실행(레퍼런스).
- **성공 기준**: 각 서비스 dry-run diff empty(제어 진입부 회귀 없음) **그리고**
  §6 divergence 체크리스트 전 항목 통과(실경로 보존) — 2중 게이트 (#917 §7, §6).
- **실패 시 행동**: divergence 누락/보존 실패 발견 시 해당 서비스 **통합 중단**
  ("훅으로 보존 못하면 멈춘다" — #917 §핵심원칙2). 실행 실패는 immich `err_trap`
  자동복구 / uptime-kuma 백업 실패 시 `systemctl start` 복구로 해당 **서비스만
  롤백**하고 창 종료(다른 작업은 이미 완료된 상태 유지) (#917 §2, §6).
