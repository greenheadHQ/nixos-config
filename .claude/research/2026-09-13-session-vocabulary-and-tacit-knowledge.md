## 1. 먼저 바뀐 판단

기록에서는 질문이나 검토를 일괄 배제하는 단일 선호가 관측되지 않았다. 기록에 반복되는 흐름은 **실제 근거를 확보하고 중요한 결정을 이해한 뒤, 합의한 범위는 에이전트가 끝까지 완수하는 것**이다. 반대로 학습 작업에서는 사용자가 직접 실습하거나 퀴즈를 푸는 방식을 따로 요청했다.

따라서 이번 정리는 인터뷰·검증·기록 자체의 폐기보다, 사용자가 원하는 결과와 모델에게 자동으로 부과하는 절차를 분리하는 방향이 적절하다. 특히 `finding-unknowns`는 단어 빈도가 낮지만, 그 안에 담긴 공유 이해·설명·기억 보존의 수요까지 낮은 것은 아니다.

추가로 실제 퀴즈 출제와 응답을 확인했다. 7월 17일 Claude의 4문항, 9월 8일 Codex의 동작 확인 퀴즈 응답이 남아 있다. 따라서 실행된 적이 없다고 판정할 수는 없다. 퀴즈가 체감 학습 효과나 작업 품질을 높였는지는 이 기록만으로 확정할 수 없다.

### 빈도 오염을 제거한 방식

- 하위 에이전트·headless SDK 작업, 에이전트 간 전달 메시지, 중단 알림, 도구 결과를 자유 발화에서 분리했다.
- Codex의 분기 로그에 상속된 `session_meta`가 1,613회 있었다. 파일의 원래 출처를 유지해 부모 대화 복제를 새 사용자 세션으로 오인하지 않게 했다.
- AGENTS·환경·플러그인 목록 등 주입 지침, 코드 블록, 인용·긴 붙여넣기 자료, `/status`·`/clear` 같은 제어 명령을 어휘 집계에서 제외하거나 별도 분류했다.
- 사용자 발화에서 돌아오는 비동기 질문 응답도 질문 원문과 답을 분리했다. 질문에 적힌 모델의 용어를 사용자가 자발적으로 쓴 단어로 세지 않았다.
- Claude 메시지 UUID, Codex 시간·텍스트, history와 원본의 같은 세션·같은 텍스트를 기준으로 중복을 제거했다. 같은 세션에서 같은 문장을 반복한 것도 어휘 관측 하나로 셌다.

최종 빈도 표본은 **9,425개 텍스트 관측, 식별 가능한 세션 1,498개**다. 작업 경로에 `nixos-config`가 포함된 표본은 5,181개 관측·860개 세션이다. 입력 history가 세션에 남은 참조 문서를 재현하지 못하거나, 사용자가 다른 곳의 문장을 직접 붙여넣은 경우까지 완벽하게 저자 판별하는 분석은 아니다. 아래 숫자는 정의한 필터에 따른 표현의 등장 빈도이며, 서로 독립된 의사결정 횟수가 아니다.

질문 도구 결과는 별도 분석했다. 전체 1,537개 결과 중 사용자 응답이 확인된 기록은 **1,375개·190개 세션**이다. 나머지에는 입력 검증 오류 62건, 거절·접수 확인·기타 결과가 있었다. 한 결과가 여러 질문을 포함할 수 있어 1,375를 질문 수로 부르지 않는다. 응답 기록과 자유 발화 빈도는 합산하지 않았다.

## 4. 반복된 작업 기준과 암묵지 후보

아래는 직접 발화·선택의 관측과 그로부터 도출한 해석을 구분한 것이다. 과거의 한 요청이 현재 모든 세션의 영구 권한이나 규칙이 되지는 않는다. 근거 ID는 레포 밖 비공개 색인에 대응하며 원문·세션 식별자는 이 문서에 복제하지 않았다.

### A. 먼저 목적을 맞추고, 합의 뒤에는 자율적으로 완수

8월 31일에는 자율 작업을 시작하기 전에 `grill-with-docs`로 궁극적 목적을 맞추라고 요청했다. 8월 25일에는 처음부터 끝까지 자율주행하되 설계와 적대적 검증을 제대로 하고 over-engineering을 피하라고 요청했다. 9월에도 지정한 범위의 자율 완수가 반복됐다. [E01·E02]

해석: 조사로 알아낼 사실을 되묻지 않으면서 사용자의 중요한 결정은 먼저 다루는 협업을 원한다. 합의한 뒤에도 단계마다 다시 승인받게 하는 자동 절차와는 거리가 있다. 특정 세션의 야간 자율주행 허용을 모든 외부 작업의 상시 승인으로 일반화해서는 안 된다.

### B. 실제 결함과 범위 확대를 구분하는 검토

8월 25일에는 명확한 버그·오류·오타만 수용하고 부가 개선을 위한 범위 확대를 기각하라고 했다. 9월 5일과 9월 12일에도 같은 경계가 확인됐다. 8월 15일에는 추가 Arbiter를 멈추고 현재 수정으로 끝내자고 직접 요청했고, 다른 결정에서는 Arbiter 자체는 유지하되 실행 조건을 수리하기로 했다. [E03·E04·E15·Q01·Q03]

해석: DA 수요와 현재의 다수 검토자·고정 강도·추가 라운드 의무는 별개다. 독립 검토의 결과가 개선 제안이라는 이유만으로 작업 범위를 늘려서는 안 된다. 반대로 오래된 종료 지시 하나만으로 모든 다음 작업의 검토 강도를 낮출 근거도 없다.

### C. 문서의 목적은 다음 세션의 재개 가능성

8월 11일에는 새 세션이 이슈 하나만 보고 처음부터 끝까지 수행할 수 있는 자기완결적 인수인계를 요구했다. 8월 25일에는 이슈를 검수할 때 자기완결성과 함께 verbose·over-engineering 여부도 평가하라고 했다. [E05·E13]

해석: 많은 항목을 채운 문서보다 목적·현재 상태·근거·남은 결정·완료 조건이 실제로 다음 행동에 충분한 문서를 원한다. “자기완결적”은 연결된 모든 참고 자료를 본문에 복제한다는 뜻으로 확장할 필요가 없다.

### D. 박제할 것은 반복해서 필요한 맥락과 결정 이유

8월 26일에는 매 세션 유용하고 쉽게 깨지지 않는 정보만 추려 하네스에 간단히 남기라고 요청했다. 한편 9월 7일에는 PR·커밋에 남긴 Claude 세션 흔적을 제거하라고 요청했다. [E06·E09]

해석: “박제”는 대화 원문·작업 로그·식별자를 모두 저장하라는 뜻이 아니다. 다시 설명해야 하는 비용을 줄이는 안정된 사실, 의도적으로 선택한 이유가 목적이다. 이번에도 원문과 세션 ID를 공개 레포의 용어집에 옮기지 않는다.

### E. 운영 스킬의 가치는 현장 설명을 반복하지 않는 데 있음

서버 문제가 날 때마다 호스트·관련 저장소 맥락을 처음부터 설명해야 하는 불편을 이유로 운영 스킬을 요청한 과거 입력이 있었다. 7월과 8월에는 현장 지문·암호 입력과 sudo 오진이 원격 자율 작업을 막는 상황을 반복해서 개선하려 했다. [E07 및 입력 history]

해석: 호스트 연결·명령 소유·비대화형 실행·복구 경계는 모델의 일반 추론과 중복되지 않는 지식이다. 희귀한 `managing-*` 호출만 보고 스킬을 삭제하면 사용자가 이미 줄이려 했던 설명 부담을 되살릴 수 있다. 세부 권한은 현재 정책과 작업 범위로 판단해야 한다.

### F. 쉬운 설명은 중요한 의사결정을 위한 기능

5월 25일에는 제안받은 질문 자체를 이해하지 못하겠다며 쉬운 설명·비유·예제·추천안을 요청했다. 이후 다른 프로젝트에서도 기술적 설명을 쉽게 풀어달라는 교정이 반복됐다. [E08]

해석: 선택지를 던지는 것만으로 공유 이해가 생기지 않는다. 무엇이 달라지고 왜 추천하는지 이해할 수 있어야 한다. 이는 인터뷰의 품질 기준이지 모든 질문에 고정된 다섯 필드를 채우라는 근거가 아니다. “한 번에 한 질문”은 현재 요청한 `grill-with-docs`의 진행 규칙이며, 이번 어휘 분석에서 사용자 직접 발화의 높은 빈도로 확인한 사실은 아니다.

### G. 작업 완수와 학습은 서로 다른 성공 기준

7월 25일의 학습 작업에서는 에이전트가 코드를 전부 작성하면 배울 수 없다며 직접 실습할 환경을 요청했다. 9월 3일에는 자신의 기여를 회고한 뒤 복습 퀴즈를 요청했다. 실제 구현 작업의 퀴즈 응답도 확인됐다. [E11·E12·Q05–Q09]

해석: 사용자가 학습을 원하지 않는다는 가정은 틀리다. 다만 모든 구현 PR의 머지에 학습 퀴즈를 붙이는 기본 정책이 현재도 필요한지는 별도 결정이다. `finding-unknowns` 정리의 핵심 질문은 바로 이 경계다.

### H. “실제”와 “확인했다”는 검증 범위를 포함해야 함

5월에는 모든 분석을 실측·데이터로 하라고 요구했다. 최근 Anki 작업에서는 서버의 전송 성공과 휴대폰의 실제 수신, 호스트 상태와 실제 클라이언트 조작을 구분하는 응답 기록이 남아 있다. [E10 및 비동기 질문 응답]

해석: 도구 호출·종료 코드·문서 생성만으로 목표 달성을 선언해서는 안 된다. 그렇다고 모든 변경에 모든 종류의 검증을 붙이는 것은 다른 문제다. 주장하는 결과에 맞는 관찰이면 충분한지 평가해야 한다.

## 5. 고정하면 오히려 잘못되는 것

| 기록에서 보이는 변화 | 영구 규칙으로 만들면 생기는 오류 |
|---|---|
| high→xhigh, 비용 때문에 다시 낮춤, quota 때문에 다른 모델 사용, 최신 모델 pin 제거 요청 | 특정 모델·effort·tier를 사용자의 영구 선호로 고정 |
| CLEAR까지 계속 요청한 작업과 추가 Arbiter를 중단시킨 작업이 공존 | 항상 무한 검토하거나 항상 검토를 생략한다고 가정 |
| 구현을 자율 완수하라는 요청과 직접 실습하고 싶다는 학습 요청이 공존 | 모든 작업에서 사용자 참여를 제거하거나 모든 PR에 퀴즈 강제 |
| 오래된 서비스 제거 결정과 나중에 다른 구조로 재도입한 결정이 공존 | 과거 세션의 인프라 현황을 현재 사실처럼 복제 |
| 이슈만으로 재개할 만큼 충분한 문서와 장황한 문서 배제 요구가 공존 | 자기완결성을 모든 자료의 전문 복사로 해석 |
| 원격 자율 실행의 불편 해소와 특정 저장소·공개 작업의 읽기 전용 제한이 공존 | 자율성을 모든 대상·외부 효과의 포괄 허용으로 해석 |

과거 결정은 이유를 이해하기 위한 증거다. 현재 환경에서 검증 가능한 사실은 코드·실행 환경으로 다시 확인하고, 선호가 바뀐 부분은 현재 사용자와 결정해야 한다.

## 6. CONTEXT.md에 옮길 후보와 다른 문서에 둘 내용

조사 시점에는 `CONTEXT.md`가 없었다. 후속 인터뷰의 첫 답변에서 지식·명시 명령 중심 원칙을 선택한 뒤, [CONTEXT.md](../../CONTEXT.md)에 운영 지식과 작업 명령만 먼저 정의했다. 다음은 추가로 논의할 후보이며, 모두 채택해야 한다는 목록은 아니다.

| 용어 후보 | 짧은 정의의 초안 | 아직 결정할 경계 |
|---|---|---|
| 공유 스킬 | 이 레포가 여러 프로젝트에서 쓰도록 제공하는 작업 단위 | 어떤 관례가 전역이고 어떤 것은 프로젝트 소유인가 |
| 프로젝트 스킬 | 이 레포의 환경·운영 작업을 위한 작업 단위 | 일반 교재와 로컬 지식의 경계 |
| 하네스 | 이 레포가 에이전트 작업을 위해 관리하는 지침·지식·실행 환경의 묶음 | 외부 관리 스킬·앱까지 포함할지, 이 레포 소유 범위만 뜻할지 |
| CIR | 개별 변경을 그렇게 수행한 이유와 중요한 이탈을 남기는 기록 | PR 본문과 코드 주석의 역할, 필수 형식 여부 |
| ADR | 나중에 맥락 없이 재판단하기 어려운 중요한 설계 선택의 이유를 남기는 기록 | 기존 PR 내 ADR과 별도 문서의 역할 |
| 핸드오프 | 이전 대화 없이 작업을 재개할 수 있게 하는 전달물 | 현황·근거·남은 결정 중 필수 요소 |
| DA | 작성자와 독립된 관점에서 변경이나 계획의 결함을 검토하는 활동 | 특정 스킬·고정 인원·강도와 활동 자체를 구별할지 |
| nrs 적용 | 이 레포의 선언형 설정을 대상 호스트에 반영하는 작업 | 빌드·정적 검사·배포 완료를 같은 말로 부르지 않기 |

`CONTEXT.md`에는 정의만 둔다. “언제 질문할지”, “어떤 검토를 자동으로 할지”, “어떻게 테스트할지”는 정책·작업 절차이며 용어집에 넣지 않는다. YAGNI·E2E·일반 Git 개념을 사전처럼 설명할 필요도 없다. Arbiter·CLEAR는 해당 역할과 계약을 유지하기로 정할 때 추가 후보가 된다.

여기서 도출한 작업 기준을 전부 AGENTS.md에 추가하는 것도 제안하지 않는다. 이미 모델·런타임·현재 지침이 충족하는 것은 새 규칙을 쓰기보다 중복을 제거할 기준으로 사용한다. ADR은 중요한 trade-off에만 남기며, 가역적인 스킬 삭제마다 새 문서를 만들 필요는 없다.

## 7. 원래 스킬 감사에 반영할 수정

1. `finding-unknowns`: 희박한 직접 호출·언급과 실제 퀴즈 실행은 함께 존재한다. 단순 미사용 폐기보다 일반 작업에 자동 연결된 원장·검토·머지 게이트의 가치를 판단한다.
2. `grilling`·`grill-with-docs` 같은 작은 명시 명령: 반복된 협업 수요가 확인됐다. 모델이 인터뷰를 할 줄 안다는 이유만으로 사용자 단축 명령까지 없앨 근거는 약하다.
3. `run-da`: 수요가 크고 사용자도 독립 검토를 유지해 왔다. 동시에 범위 확대와 추가 검토를 중단시킨 기록이 있으므로 고정 절차의 강도를 별도로 재설계한다.
4. 운영 스킬: 모델 보정보다 반복 설명을 없애는 역할이 있다. 고유 호스트·도구 지식을 우선 보존한다.
5. 기록: CIR·ADR·자기완결적인 핸드오프의 수요를 보존한다. 원장·고정 양식·세션 식별자까지 영속화할 필요는 없다.

이 후보를 바탕으로 후속 `grill-with-docs` 인터뷰에서 운영 방식을 결정했다. 이 문서의 조사 단계에서는 스킬 삭제·설정 변경·배포·공개 게시를 수행하지 않았으며, 후속 구현 결과는 감사 문서 14절에 기록했다.
