- 이 사용자의 모든 머신에서 node/npm/npx/pnpm/yarn 런타임은 mise가 관리한다 (shim 경유). 이 계열 명령이 'command not found'·'No version is set'·버전 불일치로 실패하면 PATH를 수동으로 조작하지 말고 `mise exec -- <명령>`으로 감싸 재시도하라. 프로젝트 버전 미설치는 `mise install`로 해결한다. 설정 미신뢰(not trusted) 에러는 해당 config에 env·template 같은 실행성 기능이 있다는 보안 신호다 — config 내용을 먼저 검토하고, 사용자 소유이거나 사용자가 신뢰를 명시한 저장소에서만 `mise trust`를 실행하라. trust는 경로 기준이라 checkout·pull로 config 내용이 바뀌어도 재승인을 묻지 않는다 — worktree든 main checkout이든 외부/타인 브랜치를 받았다면 mise config 변경 여부를 먼저 검토한 뒤 mise 명령을 실행하라.
- 계정 자격을 쓰는 도구(cloudflared·gh·aws·tailscale 등)로 자원을 만들기·바꾸기·지우기 전에, 그리고 자격 자체를 다루기(`login`, 자격 파일을 다른 기계로 복사) 전에, 그 자격이 어느 계정인지 도구 출력으로 확인하라 — `cloudflared tunnel list`, `gh auth status`, `aws sts get-caller-identity`, `tailscale status`. 기본 경로(`~/.cloudflared/cert.pem` 등)나 기본 프로파일에 자격이 있다는 사실은 그것이 이 작업의 계정이라는 근거가 아니다 — 한 기계에 계정 맥락이 둘 이상이면 기본값은 다른 쪽일 수 있다. 틀린 계정에서도 명령은 성공한다 — 자원이 그 계정에 만들어질 뿐이므로 exit 0은 확인이 아니다. 출력에서 이 작업이 기대하는 자원(기대값은 프로젝트 문서가 소유한다)을 직접 찾았을 때만 진행하고, 기대값을 모르면 실행하지 말고 사용자에게 물어라. `login`은 사용자가 하는 동작이다 — 에이전트가 단독으로 실행하지 않는다.
