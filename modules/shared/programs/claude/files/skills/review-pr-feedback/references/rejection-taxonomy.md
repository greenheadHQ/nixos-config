# 피드백을 반영하지 않는 이유

답글에는 판단과 확인한 근거를 간결하게 설명한다. 고정된 네 필드나 신뢰도 점수를 채울 필요는 없다. 불확실해서 결정할 수 없을 때는 확인한 맥락과 추천을 설명하고 필요한 판단만 사용자에게 묻는다.

분류가 소통에 도움이 될 때 아래 용어를 사용한다.

| 분류 | 의미 |
|------|------|
| `HALLUCINATION` | 존재하지 않는 동작·사실을 전제로 한 지적 |
| `WRONG_REFERENCE` | 실제 코드는 있으나 다른 파일·심볼·버전을 가리킴 |
| `STALE_REVIEW` | 이전 diff에서는 맞았지만 현재 변경에는 해당하지 않음 |
| `VERIFIED_FALSE_POSITIVE` | 현재 코드를 확인·검증한 결과 지적한 문제가 발생하지 않음 |
| `TECHNICAL_DISAGREEMENT` | 문제나 해결 방식에 대한 기술적 판단이 다름 |
| `DESIGN_TRADEOFF` | 대안의 비용과 기존 제약을 고려해 현재 설계를 유지함 |
| `SCOPE_DEFERRAL` | 유효한 문제지만 이번 작업 범위 밖으로 남김 |

재현하지 못했다는 이유만으로 허위 지적이라 단정하지 않는다. 유효하지만 범위 밖인 지적, 낡은 diff에 대한 지적을 `HALLUCINATION`으로 부르지 않는다.

예: “현재 호출부는 빈 입력을 필터링한 뒤 파서를 호출합니다. 빈 입력 회귀 테스트도 통과해 추가 분기는 넣지 않았습니다.”

별도 이슈는 게시가 승인된 경우에만 만들고 링크한다. 미해결 문제를 완료로 표현하지 않는다.
